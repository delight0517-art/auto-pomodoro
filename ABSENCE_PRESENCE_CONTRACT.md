# Shared inactivity reset contract

Status: implementation in progress. Mac's existing policy and the focused smoke
test are present; participation settings, complete reporting/receiving on all
clients, and runtime parity are still required before this contract is complete.

## Shared settings

`settings.absenceParticipantDeviceIds` is the user's explicit roster of opaque,
existing device IDs. A legacy Mac install without this setting initializes its
selection to the current Mac only; an explicit empty list disables resets. A client may reset a shared timer only when the roster is
non-empty and every listed device has a fresh, valid activity report. The
setting is ordered by the existing `settings.updatedAt` and `settings.updatedBy`
conflict rule. Device labels are presentation-only and are not part of this
contract. iPhone roster choices include the current phone ID even before it
has published an activity report, so the user can reselect it; the missing
report still remains `unknown` and blocks reset.

## Report

Each participant publishes this optional snapshot field:

```json
{
  "activityPresence": {
    "version": 1,
    "source": "physical-input",
    "observedAt": 1791381000000,
    "lastActivityAt": 1791380000000
  }
}
```

The authenticated unified sync state may also return an `activityReports` map
keyed by opaque device ID. The sync service stores validated reports from
snapshots and heartbeats, keeps timestamp high-water marks, and normalizes the
documented legacy Windows physical-input shape. Clients evaluate this map with
the shared roster; it contains no device names or selected-app identifiers.
Before storing a snapshot, the server reduces `activityPresence` to exactly the
four fields shown above. Extra fields such as app names or Screen Time
selection data are discarded; an invalid report is removed so it cannot be
relayed inside the snapshot.
`activityReports` is response-only: the server discards any client-supplied map
and builds the returned map from validated per-device reports.
When a timer-winning snapshot belongs to a different device than the publisher,
the publisher sends its report in the request-level `activityPresence` field.
The server associates that report with the authenticated `deviceId` and never
reuses the timer owner's embedded report for the publisher.
Before an iPhone applies a background-absence reset, it fetches this map from
Brainwire `/api/pomodoro-sync/state`; a failed fetch is unknown, blocks reset,
and retains the background start time so the next foreground reconciliation can
retry.

`observedAt` and `lastActivityAt` are Unix epoch milliseconds. Allowed sources
are `mac-system-idle`, `physical-input`, and `selected-app-use`. Heartbeats may
refresh `observedAt`; they must never advance `lastActivityAt`. iPhone reports
the most recent selected Screen Time app threshold event without application
names or Family Controls tokens. Apple exposes threshold callbacks for this
monitor path, not a periodic proof that selected apps remained unused; iPhone
must not refresh `observedAt` during an ordinary heartbeat. Once that event
report is older than five minutes, the selected phone is unknown and blocks
reset. The report contains no device name; the surrounding sync protocol uses
its existing opaque `deviceId` to associate the report.
The current extension only records threshold-reached callbacks and uses that
event time for both fields. With a five-minute inactivity threshold, such a
report passes only at the exact five-minute freshness boundary; after that it
is stale, and for longer rest thresholds it cannot prove inactivity at all.
The app publishes a newly observed callback to Brainwire through its
authenticated heartbeat endpoint during normal sync. This event is generated
by the existing AutoStart Screen Time monitor, so AutoStart must be enabled and
its selected-app set must be non-empty. Disabling that monitor or clearing its
selection means no new iPhone report is available; the device remains unknown.
The publisher never turns an old callback into a fresh observation.
Apple documents that `DeviceActivityCenter` invokes interval-start,
interval-end, and event-threshold callbacks only while someone is using the
device. Those callbacks therefore cannot serve as a wall-clock heartbeat for
an idle or locked phone, and the threshold callback still proves selected-app
use rather than continued non-use. This limitation cannot be fixed by
extending freshness without treating an offline phone as inactive
([DeviceActivityCenter](https://developer.apple.com/documentation/deviceactivity/deviceactivitycenter)).
`DeviceActivityReport` does not provide a substitute last-used event stream:
Apple defines it as a view generated by a sandboxed report extension, and its
application activity data exposes aggregates such as total duration rather
than a last-used timestamp. The extension also cannot make network requests or
move sensitive report data outside its address space ([report extension](https://developer.apple.com/documentation/deviceactivity/deviceactivityreport), [application activity data](https://developer.apple.com/documentation/deviceactivity/deviceactivitydata/applicationactivity)).

## Reset decision

For threshold `breakMin` (or `longBreakMin` when applicable), reset only if:

1. The roster is non-empty.
2. Every selected device has a report no more than five minutes old.
3. Both timestamps are positive, plausible (no more than 30 seconds in the
   future), `lastActivityAt` is no more than 30 seconds after `observedAt`, and
   `lastActivityAt` is at least the threshold before now. Timestamp fields
   must be JSON numbers; string coercion is not part of the contract.

Any missing, stale, future, malformed, unsupported, or out-of-order report is
`unknown` and blocks a reset. One fresh activity report blocks a reset. A
heartbeat is presence evidence, never human activity. An unselected device has
no effect. Duplicate IDs are evaluated once. Older reports cannot replace a
newer observation or activity timestamp.

iOS requires a successful current unified-state fetch before it uses the
cached report map for a background-resume reset. A fetch error is `unknown`;
it must not reset from cached reports alone.

The five-minute report freshness limit assumes every client refreshes its
observation at least once within that window. If a platform cannot provide that
cadence or an authoritative selected-app event, its status remains unknown and
the timer must not reset based on that device.

## Compatibility and evidence

Older clients that omit `activityPresence` remain readable for timer sync but
cannot prove inactivity for a selected device, except for the explicit Windows
compatibility adapter: `computerPresence.source` must be `physical-input` or
`controller-input`, both `generatedAt` and `lastHumanInputAt` must be numeric,
and `generatedAt` becomes `observedAt` while `lastHumanInputAt` remains
`lastActivityAt`. A server-maintained device record may use its refreshed
`lastSeenAt` as `observedAt` only when it is paired with that previously
validated physical-input timestamp; `lastSeenAt` alone never proves
inactivity. Timer snapshots, app names, a missing callback, and a successful
upload never prove inactivity. Keep Mac, iPhone, and Windows source,
installed-runtime, and cross-device journey evidence separate. Required
combinations include each participant active while the other participants are
inactive, all participants inactive beyond threshold, and one selected
participant offline/stale.
