# Source linked sleep and alarm regression gate

Run this before accepting a Pomodoro or RiseSync sleep/wake change:

```sh
node scripts/sleep-world-source-gate.js
```

The same gate is part of `npm run check`, `npm test`, and the local build preflight. It reads the current RiseSync checkout (`../45Auto_Alarm`, or `RISESYNC_ROOT`), checks the live `NapEvidence.Inputs` schema and nap timing defaults against the NPC adapter, runs RiseSync's source-extracted Swift policy/lifecycle simulations, then runs the Pomodoro reducer and virtual-world scenario suites. The RiseSync simulator compiles its current production policy and service code with virtual time and sensors; it does not use a copied Swift policy file.

When the gate reports source/simulator drift, update the scenario adapter and add a boundary case for the changed rule. Do not update a source fingerprint to silence the failure: source changes are executed directly by the RiseSync virtual lifecycle runner, and contract changes must be reflected in the NPC simulator before the gate can pass.

The virtual world contains the iPhone and independent Mac/Windows workstations, but this gate cannot prove physical sensors, OS background execution, AlarmKit delivery, Windows installed-app behavior, or audible ringing. Those remain separate runtime checks.

The `no-app-open` regression models the phone being carried while neither RiseSync nor iOS Pomodoro has been foregrounded that day. It distinguishes a previously registered HealthKit observer, a registered region callback, the independent Screen Time extension, an explicitly delivered best-effort background refresh, normal no-launch, and user force-quit. App-process GPS/Wi-Fi/CoreMotion samples are not fabricated while RiseSync is absent; missing observations remain unknown. A late HealthKit result retains its event occurrence time. Run it alone with `node scripts/sleep-world-no-app-open-test.js` or through `node scripts/sleep-world-cli.js scenario no-app-open`.

The `relapse-90m` replay runs the production Pomodoro sleep-state reducer with a confirmed six-hour sleep interval, 15 timestamped Mac input observations, a wake event, and confirmed resleep. For a 450-minute target it requires exactly 90 minutes remaining, with the wake deadline 105 minutes after the initial wake. Its output keeps the historical first-wake event time separate from the reducer's current-cycle wake anchor, which clears after confirmed resleep. Run it with `node scripts/sleep-world-cli.js scenario relapse-90m`; `node scripts/sleep-world-source-gate.js` also checks this trace and the RiseSync production Swift lifecycle, including OS-adapter delivery at the 90-minute deadline. This validates the shared policy path under virtual adapters, not physical sensor delivery or audible iPhone ringing.

The `wake-work-resleep-60m` regression replays a 07:00 wake, 60 minutes of real Mac input, confirmed sleep at 08:00, and a second wake at 09:30. With six confirmed hours before 07:00 and a 450-minute target, it requires a 09:30 alarm and starts a fresh 120-minute wake restriction at that second wake. Run it with `node scripts/sleep-world-cli.js scenario wake-work-resleep-60m`; it is included in the source-linked gate. This verifies the reducer timeline, not whether sensors infer the bed entry or the OS actually sounds the alarm.

The `dawn-phone-use` Wake Village replay uses the corrected user timeline: phone use from 23:30 through 03:20, sleep after that, and waking at 11:20. The reducer must show awake at 03:14 and 03:20, then sleeping after use ends. Selecting the story calls `/api/risesync/dawn-phone-check`; the local server extracts and executes the current `ongoingSleepSessionStart` Swift function and relevant live helpers, rejecting a mistaken 00:39 Screen Time anchor at 03:14 while preserving a HealthKit positive control. Unrelated fallback branches are stubbed in this small harness. Run it without the browser with `node scripts/sleep-world-cli.js scenario dawn-phone-use`. This is source-linked virtual evidence; the scenario supplies the user's phone-use timeline as ground truth and does not prove RiseSync currently receives cross-app Screen Time duration or exercise physical iPhone delivery.

The Wake Village selector also includes six bedtime-preparation replays: iPhone use followed by phone power-off, opening an iPhone app before bed, or pressing RiseSync's “지금 잘게” button, each followed by one hour of timestamped physical Mac or Windows input, confirmed sleep, the remaining-sleep alarm, and re-wake. Run all six with `node scripts/sleep-world-cli.js scenario bedtime-prep`. The existing six-hour sleep ledger remains separate from wake-time computer work; timer-running is displayed as context but is not counted as physical input. The replay requires five input samples from the selected computer, a 09:35 alarm after 90 more sleep minutes, 450 total confirmed sleep minutes, and a fresh 120-minute restriction at re-wake. The bedtime button is a labeled NPC event in these reducer replays; the test does not execute RiseSync's production button handler or emulate actual iPhone power control, app launch delivery, background sensor inference, or OS alarm sound.

`main/userSleepState.js` is the single reducer source. The iOS resource copy is byte-checked by the source-linked gate and by a dedicated Xcode pre-build phase; direct Xcode builds therefore fail when the bundled reducer drifts. The source-linked gate also asserts that both the Xcode specification and generated project retain this build phase. The desktop `npm run check`/build preflight runs the full RiseSync + NPC source-linked gate.

User settings can be imported from a local, non-secret JSON profile using `node scripts/sleep-world-cli.js profile import /path/to/settings.json`. The import is allowlisted and reports which device settings were supplied. A BlueCloud snapshot may include only its revision, update/capture times, and allowlisted Pomodoro settings under `blueCloud`; the canonical `baseFocusMin`/`baseBreakMin` fields take precedence over legacy `focusMinutes`/`breakMinutes`, and alias disagreements are reported. Keep the sanitized profile private when it contains personal schedules. Example defaults are marked as examples; missing Windows, RiseSync, or iOS Pomodoro values stay unknown. Never put HealthKit records, account identifiers, app-group tokens, credentials, or raw activity histories in the profile. A BlueCloud snapshot proves that those settings were read from that account at that revision; it does not prove current physical-device behavior.

To run the full source gate and its 50 physical NPC replays against a pinned, sanitized profile, set `SLEEP_WORLD_PROFILE=/path/to/private-profile.json` before `node scripts/sleep-world-source-gate.js`. The same variable works with `node scripts/sleep-world-50.js` for the focused replay. The report includes only the profile revision/time and which device-setting fields were known. It does not contact BlueCloud or a device during simulation.

The two-hour Mac/Windows work-to-resleep replay explicitly ends both synthetic work sessions before resleep. RiseSync suppresses automatic naps only for recent actual human input. The replay retains the positive nap expectation after sessions end and requires the running-session control to preserve nap protection when input stops; neither timer state nor timer receipt is promoted to confirmed human wake evidence. This does not emulate automatic away-pause or stop real device timers.


The late-device first-use gate executes `scripts/wake-authority-smoke.js` against the production controller: validated Windows first use followed by a fresh Mac boot20minutes later, exact60/120-minute caps and40/100minutes remaining (less actual qualification elapsed), second account read after30seconds, restart persistence, rejected pre-rollout/malformed input, late-earlier anchor republication with unchanged max revision, CAS409 remerge, and deadline-specific readback acknowledgement. Qualified input remains provisional; ordinary input and timer state cannot confirm wake. Rollout begins2026-10-25T03:10:15Z; pre-rollout activity is not backfilled. The gate does not manufacture physical input or prove the installed iPhone/Windows journey.
